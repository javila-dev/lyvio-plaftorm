## Scope & mode

The authenticated platform shell: `subscriptions/base.html`, extended by 13 live templates (billing dashboard, plan details, payment history, invoices, upgrade/activate/cancel/reactivate/renew subscription flows, billing info, the payment-card form, and `bot_builder/configure.html` + `dashboard/admin_dashboard.html`). Operate mode. Shares the same dark token system as the onboarding wizard (`onboarding/templates/onboarding/_design_system.html`, included cross-app) — this and the onboarding brief describe one continuous visual world, not two.

A second, structurally separate shell (`templates/base.html` at the project root — top navbar, no sidebar) serves 4 other live templates (`bot_builder/config.html`, `bot_builder/flow_builder.html`, `dashboard/home.html`, `dashboard/settings.html`) and is untouched — out of scope here.

## Direction — corrected against real Chatwoot screenshots (2026-08-27)

The first pass over-used solid/gradient blue fills as generic decoration (icon badges on every stat card, quick-action tiles, section headers). The user supplied real screenshots of `app.lyvio.io` (inbox, inbox-settings list, channel-picker) that contradict this directly: every icon Chatwoot renders purely for recognition — channel icons, settings-row icons, empty-state icon — sits in a **neutral gray circle**, never a colored one. The channel-picker grid alone has ~13 icons and not one is blue.

**The One Blue Rule, restated for this surface.** Blue (`#2781F6`) is reserved for what is actually active, current, or actionable:
- primary buttons and links
- the current/selected step in a flow (the numbered stepper's active circle)
- small status/meta pills — trial countdown, a "Beta" tag — the kind of chip Chatwoot itself renders in blue
- the one plan a pricing table is steering the visitor toward (a bordered highlight, not a fill)

Everything else — a decorative icon next to a card heading, a stat-card glyph, a quick-action tile's icon — is a neutral gray chip: `background: var(--surface-hover); color: var(--text-muted);`, named `.icon-chip` in `subscriptions/base.html`. Reach for that class before reaching for a color. Same logic killed the colored `border-2 hover:border-green-200` accents on quick-action cards and the solid-blue drawer header — both flattened to the neutral `.card` treatment already used everywhere else.

## Unresolved / traps for next time

- **Two literal-syntax-inside-a-comment bugs shipped and were caught late.** A CSS comment containing a real `*/` inside prose (a URL with `/*/`) silently truncated the comment and dropped the entire next rule with no error — the browser just parsed past it. A Django template comment containing literal `{% if %}` as descriptive text was parsed as a real (malformed) tag and 500'd the page. Both read as fine at a glance. When describing template/CSS syntax *inside* a comment, paraphrase instead of writing the literal token sequence.
- **All 13 templates in scope are now converted** (2026-08-27): `dashboard.html`, `plan_details.html`, `payment_history.html`, `invoice_detail.html`, `upgrade_plan.html`, `cancel_subscription.html`, `activate_plan.html`, `card_form_professional.html`, `reactivate_subscription.html`, `renew_subscription.html`, `billing_info_form.html`, `bot_builder/configure.html`, `dashboard/admin_dashboard.html`. Every one was verified live via the `sso/dev-login` bypass with real seeded fixture data (not just a static screenshot of the default state) — including secondary states where relevant (empty states, discount banners, expired/pending/paid statuses, both billing cycles, medical-bot-required calendar mode). `admin_dashboard.html` is staff-only (`@staff_member_required`); the dev-login user needs `is_staff=True` set via ORM to reach it locally.
- `reactivate_subscription.html`, `renew_subscription.html`, and `billing_info_form.html` all leaned on raw DaisyUI semantic utilities (`text-base-content`, `bg-base-100`/`bg-base-200`, `alert-info`/`alert-warning`/`alert-error`, `.divider`, `btn-outline btn-neutral`) that are **not** covered by any of `subscriptions/base.html`'s overrides (only `.card`/`.card-body`/`.alert`/`.btn-primary`/`.btn-outline-primary`/`.input`/`.select`/`.textarea` are overridden there) — these render with DaisyUI's actual light-theme colors, a third distinct mechanism (after the Tailwind gray/slate `-300` trap and the broken CDN version) for the same "looks fine in the editor, invisible/wrong on the real dark page" failure. Fixed by hand-converting every one to the `var(--*)` design tokens, matching the pattern already used for `alert alert-info`/`alert alert-warning` in `upgrade_plan.html`/`activate_plan.html`. `billing_info_form.html` had the same problem one layer deeper — its own hand-authored `.input-group-modern input/select` CSS hardcoded a *white* input background with no explicit text color, meaning form fields were invisible-text-on-white islands regardless of the shell's theme; fixed to `var(--surface)`/`var(--text)`.
- **Status/plan pill convention, now applied consistently everywhere in this shell:** `bg-{color}-100 text-{color}-700` (the light-theme Tailwind default for a colored pill) reads as a bright pastel island against this shell's near-black surfaces. The fix used throughout — `admin_dashboard.html`'s many status/plan/expiry pills included — is `bg-{color}-500/15 text-{color}-400`: a translucent tint of the real color plus a bright-enough text shade to stay legible on black. Reach for this pattern first for any new status pill rather than copying `-100`/`-700`.
- **Bare DaisyUI component classes with no color modifier are a second contrast trap**, distinct from the Tailwind gray/slate one: `btn-neutral`, `badge-neutral`, an unmodified `.btn` (e.g. `join-item btn btn-sm` in a pagination control) all pull from DaisyUI's own light-theme `--n`/`--bc` variables, which `subscriptions/base.html` never overrides. Result ranges from a stray light-gray button island to actually-invisible dark-on-dark text, depending on which sub-property each DaisyUI class happens to set. Fixed throughout by replacing them with explicit `border border-slate-300 text-slate-600 hover:bg-[#272a2d]` (secondary/neutral action) or `btn-primary`/solid `var(--danger)`/`var(--success)` (when the button carries real semantic weight, e.g. `renew_subscription.html`'s "Completar Ahora"/"Agregar Tarjeta" CTAs inside a danger alert).
- `card_form_professional.html` (the Wompi card-collection form) is fully converted too, but it's structurally different from every other template in this shell: 100% hand-authored `!important` CSS under unique class names (`.payment-card`, `.form-control`, `.btn-primary`/`.btn-secondary` — note these reuse `.btn-primary`'s name but are scoped by the surrounding hand-authored rules, not `subscriptions/base.html`'s override), so none of the shell's dark-token overrides reached it for free — every color had to be hand-converted to `var(--surface*)`/`var(--text*)`/`var(--success)`/`var(--danger)` tokens. The header and the plan-summary accent bar were flattened from indigo→purple gradients to solid `#2781f6`. JS logic (card-type detection, formatting, validation, submit-loading state) was left untouched — only a hardcoded inline JS color string (`loadingMsg` text color) was updated to match. The real card-network brand icon colors (Visa blue, Mastercard red, Amex blue, Diners blue) were deliberately left as their real brand colors, not neutralized — these identify an actual payment network, unlike a decorative icon-chip.
- `activate_plan.html` also had two real functional bugs, both fixed: the "click anywhere on the billing-cycle card" JS handler targeted `.card.border-primary`/`.card.border-success`, classes that never existed in the markup (it matched nothing — only the tiny radio dot itself was clickable); and there was no visual "selected" state on either card at all. Fixed by introducing `.billing-card`/`.billing-card-primary`/`.billing-card-success` with a `:has(input:checked)` rule (same pattern as `upgrade_plan.html`'s `.billing-option`), and pointing the JS at the real class.
- Plan/Trial fixture data (3 `Plan` rows, slug-keyed) was seeded directly in the dev DB to make the carousel and pricing cards testable — real content, not placeholder copy, but seeded outside the normal admin flow.
- **`daisyui@2.57.0` (pinned project-wide, pre-dating this whole design pass) 404s — that patch release never existed on jsdelivr.** It silently zeroed out every DaisyUI component style (badges, `.btn` sizing modifiers, alert internals, bordered inputs) for an unknown period. Fixed everywhere to `daisyui@2.52.0` (confirmed real via `https://data.jsdelivr.com/v1/packages/npm/daisyui`). If a DaisyUI component ever looks completely unstyled again, check the pinned version first before assuming a CSS specificity fight.
- **`text-slate-300`/`text-gray-300` (and `-200`) are a contrast trap under this shell's remap.** The `gray`/`slate` Tailwind scale is inverted here for dark-theme purposes — 50–300 are the *darkest* shades (`50`→`#18191b` … `300`→`#363a3e`), 700–900 are the *lightest* (`#b0b4ba` / `#edeef0`). Standard Tailwind intuition says "300 = light gray, safe for secondary text on a dark card" — here it's nearly the same value as the surface itself, producing invisible dark-on-dark text/icons. Caught 2026-08-27 in `cancel_subscription.html` (button text, a status pill) and swept into four already-shipped files that had the same mistake (`invoice_detail.html`, `payment_history.html`, `plan_details.html`, `dashboard.html` — all large decorative empty-state icons or badge text). For muted-but-legible text/icons on a dark surface, use `-400` (small icons/captions, proven legible) or `-600`/`-700` (readable secondary text); reserve `-800`/`-900` for near-white emphasis text. Never reach for `-200`/`-300` expecting a light tone in this shell.
